1. The big picture — the stack

Finance Manager is a server-driven single-page-feeling web app. There is no separate JavaScript front-end framework; instead the UI is built from Livewire components (PHP classes that render Blade HTML and talk to the server over AJAX), styled with Flux (a Livewire UI kit) and Tailwind CSS. Data lives in a single-file SQLite database accessed through Laravel's Eloquent ORM.

Mental model: a click in the browser sends a tiny AJAX request to a Livewire component on the server. The component updates its PHP properties, re-renders its Blade view, and sends back just the HTML diff, which Livewire patches into the page. It feels like a SPA but the logic is all PHP.

2. How the project was created (step by step)

This is the path from empty folder to the app you have. Your composer.json still carries the tell-tale scripts (post-create-project-cmd, setup) from these steps.

Step 1 — scaffold a Laravel app

composer create-project laravel/laravel finance-manager

This downloads the Laravel skeleton and runs post-create-project-cmd, which: generates the app key, creates the empty SQLite file (touch database/database.sqlite), and runs the first migrations. That is why the DB is SQLite by default.

Step 2 — choose SQLite

In .env: DB_CONNECTION=sqlite. No host/user/password needed — Laravel just reads/writes the one file. Great for development and small single-user apps.

Step 3 — add Livewire & Flux

composer require livewire/livewire
composer require livewire/flux-pro   # private repo: composer.fluxui.dev

Flux Pro is a paid package, so composer.json declares a custom repositories entry pointing at https://composer.fluxui.dev.

Step 4 — front-end toolchain (Vite + Tailwind)

npm install            # installs vite, tailwind, alpine, axios, concurrently
npm run build          # compiles assets into public/build

Step 5 — build the domain

For each feature: write a migration (table), an Eloquent model, a Livewire component (app/Livewire/...) and its Blade view (resources/views/livewire/...), then register a route in routes/web.php. Authentication (login, register, OTP, password reset) was built as Livewire components rather than a pre-made starter kit.

Step 6 — run it

php artisan migrate     # create the tables
php artisan serve       # start the dev server  ->  http://127.0.0.1:8000
One-command recreate: your composer.json defines a setup script that chains it all: composer install → copy .env → key:generate → migrate --force → npm install → npm run build. Run it with composer run setup.

3.3 The bootstrap/ folder — not the CSS framework!

In Laravel, "bootstrap" means starting the framework up, nothing to do with Bootstrap CSS.

  • bootstrap/app.php — the modern Laravel entry configuration. It wires routing (routes/web.php, routes/console.php), middleware, exceptions and a /up health-check, then returns the Application instance.
  • bootstrap/providers.php — the list of service providers to load (here just AppServiceProvider).
  • bootstrap/cache/ — compiled config/route caches for speed.
return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(web: __DIR__.'/../routes/web.php', commands: ..., health: '/up')
    ->withMiddleware(fn ($m) => ...)
    ->withExceptions(fn ($e) => ...)
    ->create();

4. The database: migrations, models & seeders

4.1 Migrations — version control for your schema

A migration is a PHP class describing a schema change (up() to apply, down() to reverse). Running php artisan migrate executes the pending ones in filename/date order and records them so they never run twice. This means anyone can rebuild the exact same database from scratch.

MigrationWhat it creates / changes

create_categories_tableIncome/expense categories (name, type, colour, icon).
create_transactions_tableEvery income/expense row (amount, type, date, category).

4.3 Seeders & seeding

A seeder fills the DB with starter data. DatabaseSeeder creates a test user via a factory (a class that fabricates fake model data). Run with php artisan db:seed (or migrate --seed).

This app also does lazy seeding: when a user first opens a relevant page, Category::seedDefaultsFor($user) gives them 13 ready-made categories (Salary, Food, Transport…), but only if they have none yet:

public static function seedDefaultsFor(User $user): void {
    if ($user->categories()->exists()) return;     // already seeded
    foreach (self::defaults() as $cat) $user->categories()->create($cat);
}

5. How a request flows (the lifecycle)

This is why it works — the chain that turns a URL into a page.

  1. Browser → public/index.php. Every request hits this single front controller.
  2. bootstrap/app.php boots the framework and builds the service container.
  3. Middleware runs (sessions, CSRF, and auth for protected routes).
  4. routes/web.php matches the URL to a Livewire component, e.g. Route::get('dashboard', Dashboard::class).
  5. The Livewire component's render() runs: it queries Eloquent (often via the MonthlyFinance/CycleLedger services) and returns a Blade view.
  6. Blade compiles to HTML, wrapped in the layout (components.layouts.app → the dashboard shell with sidebar).
  7. @vite injects the compiled CSS/JS; @livewireScripts and @fluxScripts add the JS that makes the page interactive.
  8. Interactivity: a wire:click="prevMonth" sends an AJAX call back to the same component; it mutates a property, re-renders, and Livewire patches only the changed HTML into the page. Alpine handles purely-client things (sidebar open/close, dark mode) with no server round-trip.
Why no page reloads? Livewire keeps a snapshot of the component's state in the page and exchanges small JSON/HTML diffs with the server on each interaction — the server stays the source of truth, the DOM is patched in place.

6. The domain logic (what makes it a finance app)

Two custom services in app/Support/ hold the money rules so the Dashboard, Budget and Reports pages all agree:

  • MonthlyFinance — given a user + planning month, it computes the pay-cycle window (money is planned on a 25th→24th style cycle, not the calendar month), planned income (salary + entries), expenses, budget, savings and pace. Salary is only counted from the user's registration cycle onward.
  • CycleLedger — implements carry-forward: each completed cycle's leftover (opening + income − expenses) rolls into the next via the cycle_summaries table, so the dashboard "Total Balance" is a running balance, not a monthly reset.

A new user sees a 3-step onboarding wizard (welcome → set pay-cycle day → success) the first time they log in, gated by the onboarded_at column.

7. Running it: php artisan serve vs composer run dev

What each one actually does

php artisan serve starts one thing: PHP's built-in web server wrapping public/index.php at http://127.0.0.1:8000. That's it — it serves the PHP app.

composer run dev runs the script from composer.json, which uses concurrently to launch four processes together:

npx concurrently
   "php artisan serve"                       # 1. web server
   "php artisan queue:listen --tries=1"      # 2. background job worker
   "php artisan pail"                        # 3. live log viewer
   "npm run dev"                             # 4. Vite dev server (hot reload)
   --names=server,queue,logs,vite --kill-others

Why php artisan serve alone works for you

Because you already ran npm run build, the compiled CSS/JS sit in public/build. The @vite directive checks for a public/hot file (written only while the Vite dev server runs). No hot file → it loads the pre-built assets from the manifest. So the app is fully styled and interactive without Vite running. You'd only need Vite (i.e. composer run dev or a separate npm run dev) when you're editing CSS/JS and want changes without rebuilding.

php artisan servecomposer run dev
Processes1 (web server)4 (server + queue + logs + Vite)
Front-end changesNeed npm run build to see themHot reload — instant
Background jobs (queue)Not runningRunning
Live logsNoYes (pail)
Resource useLightHeavier (needs Node + npm deps)
Best whenBack-end work, or using built assetsActive full-stack development

Advantages / disadvantages

php artisan serve  + simplest, one terminal, low resources, perfect with pre-built assets.  − no hot reload, no queue worker, no live logs; you must rebuild after CSS/JS edits.

composer run dev  + full dev experience in one command (HMR, queues, logs).  − heavier, noisier, requires Node + the npm packages installed; overkill if you're only touching PHP.

Neither is for production. In production you don't use a dev server at all — you serve via nginx/Apache + PHP-FPM, run npm run build once, and run the queue worker as a managed process (e.g. supervisor). artisan serve and composer dev are development conveniences only.
